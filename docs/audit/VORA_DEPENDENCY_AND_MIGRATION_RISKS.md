# Vora Dependency and Migration Risks

**Baseline:** Repository revision `b36fbd4`, audited 2026-11-11.  
**Scope:** Risks to future scientific-architecture work inferred from inspected source. No user DB was opened and no migration was run.

## 1. High-priority risk register

| ID | Risk | Severity | Evidence and consequence | Required control before rollout |
|---|---|---:|---|---|
| R1 | Unknown deployed DB populations and schema variants | Critical | Only source initializer paths are known. Active installations may have older or partially applied module-specific migrations, existing rows, or external path differences. A migration written for a guessed “current” schema may fail or lose data. | Obtain owner-approved, anonymized copies of representative databases and app versions; inventory `sqlite_master`, columns, row counts, FK violations and asset paths read-only; preserve hashes/originals. |
| R2 | No unified, ordered migration ledger | Critical | Runtime schema is composed from module initializers with independent `CREATE IF NOT EXISTS`, ad-hoc `PRAGMA table_info`/`ALTER`, and Market markers. Initializer failures may leave preceding changes applied. | Design a single versioned migration ledger/runner, per-migration transaction/atomicity rules and supported-from matrix; test every fixture and interrupted/restarted upgrade. |
| R3 | Duplicate schema sources and stale architecture guidance | High | Runtime uses Rust initializers plus `schema_source.sql` and `schema_market.sql`; `src-tauri/src/schema.sql` is not included by runtime. Root guidance and older audit docs describe stale paths/table counts. | Declare one source of truth per domain; update architecture guidance only after the actual runtime ownership is confirmed; add tests asserting fresh DB schema parity. |
| R4 | Connection-specific foreign-key enforcement | High | SQLite FK enforcement is per connection. Shared app connection sets it; `open_default_db_connection()` creates a second connection without setting it. Future typed references may behave differently by call path. | Centralize connection creation/configuration; assert `PRAGMA foreign_keys=1` on every connection and run `foreign_key_check` on fixtures, after migrations, and before import acceptance. |
| R5 | Destructive/partially suppressed Market migration behavior | High | Market initializer explicitly drops `market_sources`; marker-controlled logic deletes derived `market_boxes`; legacy column drop/add and cleanup statements suppress errors. Reusing the pattern for scientific records could irreversibly destroy user-authored data or obscure partial failures. | Do not generalize this migration pattern. Classify data as source-of-truth vs derived; require explicit backup, marker/version assertions, row-count audit, failure injection, and user approval for destructive conversion. |
| R6 | Database backup does not prove complete workspace backup | High | SQLite online backup handles DB rows; settings are separate JSON; media, documents, Parquet, Trace and worker state use other roots. Current import checks are not a full asset manifest/hash restore contract. | Define workspace bundle boundaries; include versioned manifest, relative/portable paths, hashes and explicit exclude rules; test restore on a clean machine/path with all referenced assets. |
| R7 | Soft/polymorphic scientific references | High | Source link targets, source revision entity IDs, question promotion, hypothesis inquiry/lineage/source/library IDs, several canvas endpoints, and Trace references are strings without endpoint FKs. Future typed relations cannot safely infer target type from text or UI labels. | Inventory every existing ID/target, resolve or quarantine unknowns, preserve original IDs and provenance; add explicit typed endpoints only through reviewed mapping and integrity checks. |
| R8 | Source content/version semantics are insufficiently defined | High | `source_revisions` is an append-only event record, not an immutable captured edition. Source metadata/path can change; extracts point to segments and not a captured content/version hash. Revision insert is not guaranteed atomic with each domain mutation. | Decide URL/document capture semantics, immutable hashes and retention; add SourceVersion and pinned citation contracts; test source mutation/revision failure atomicity and historic extract readability. |
| R9 | Mixed timestamp units and scientific measurement ambiguity | High | Market documents epoch seconds; canvas/media use millisecond values in places; source and Mind paths use differing integer conventions; Trace uses strings. JSON/text data has no universal unit/timezone/value contract. | Define canonical UTC/time precision, measurement units and conversion provenance; never infer units from magnitude alone; add boundary tests for second/ms collisions, DST, negative/pre-epoch values and exact numeric precision. |
| R10 | Nonuniform delete/cascade/archive behavior | High | Some FKs cascade, many references are soft, source history is trigger-protected, questions and hypotheses have delete paths, and no global scientific retention/archive semantics exist. | Set per-entity lifecycle and reference policy (restrict/cascade/archive/detach) before FK addition; test referential deletion against realistic graphs and recoverability. |
| R11 | JSON/text blobs can be misinterpreted as typed scientific data | High | Hypothesis protocol/data-entry/checklist, source metadata, board snapshots, market registries, Trace evidence and package payloads have local or implicit schemas. | Preserve original blob and schema/version context; create audited, version-specific decoders; reject/quarantine unknown shapes rather than success-shaped defaults; validate conversion loss. |
| R12 | IDs and identifier ownership are heterogeneous | Medium–High | Existing IDs include opaque UUID-like values, domain-prefixed source examples, numeric records, and composite keys. Re-keying breaks soft links, snapshots, imported package bookkeeping and external references. | Keep old IDs as stable aliases; define new IDs and unique constraints; test round-trip/reference traversal and duplicate/collision handling before any backfill. |
| R13 | Partial transaction coverage and append-only history gaps | High | Some operations use SQLite transactions (e.g., question promotion, task-flow position updates, selected snapshot/import actions), while other multi-write paths do not universally wrap state and revision records together. | Add transaction-boundary inventory per command; test injected failures after each write; ensure domain event/history rows commit atomically with state changes. |
| R14 | Main and worker services have separate schemas/locking lifecycles | Medium–High | Worker uses a relative queue DB and operational task state, while main app uses AppData workspace DB. The worker is not a scientific run service; runtime path/deployment is unknown. | Decide whether and how worker consumes immutable run contracts; use explicit job/result IDs and payload schemas; test retries, cancellation, stale locks, concurrent app/worker access and DB contention. |
| R15 | Frontend persistence can be mistaken for durable research state | Medium | Zustand browser/localStorage persists selected UI state; other stores cache SQLite-backed data. Browser-mode Trace uses mock graph data. | Make durable/derived/cache state explicit; test restart, offline, Tauri/browser mode and save failures; never migrate UI cache into canonical entities without validation. |
| R16 | Frontend/backend contracts are split and no UI test baseline found | Medium | Domain DTOs/types are distributed across `src/types`, `src/mind/types` and feature modules. No frontend test files or frontend test script were found during inspection. | Establish contract parity and minimal component/IPC test coverage before UI migration; record baseline behaviors and accessible error states. |
| R17 | Existing audit/spec package has stale implementation claims | Medium | Older inquiry audit describes pre-triage question shape; older recon lists 14 canvas tables; target prose cites the duplicate schema file. | Keep target intent separate from current-state evidence; update derived audit materials only with verified code evidence and date/revision. |

## 2. Legacy mapping and safe-migration boundaries

The target architecture should add explicit new identities and provenance rather than overload existing columns or rename rows. Preserve source DB, DB/settings exports and external assets before any migration; every transform should be reproducible from a source copy and produce an audit report of converted, unchanged, ambiguous, rejected and missing data.

| Existing data | Potential future use | Automatic mapping safety |
|---|---|---|
| `sources`, `segments`, `extracts`, `links`, `source_revisions` | Source, source capture/version, citation, extraction, provenance graph | Preserve all rows and IDs. A source row can seed a Source identity only if product approves. Cannot infer a SourceVersion, edition, capture hash, immutable citation, or typed target solely from mutable metadata/revision events. |
| Questions and triage columns | ResearchQuestion; perhaps a ResearchGap candidate | Preserve question/status/score/timestamps. Do not equate every question with a gap or assign a project/domain without user/product mapping. `promoted_to_hypothesis_id` may be dangling/soft. |
| Hypothesis fields, data-entry JSON, insights, snapshots, definitions | Hypothesis and lineage; candidate protocol/data narrative | Preserve raw strings/JSON and IDs. Do not map checklist entries to samples/observations, `raw_data` to a Dataset, insights to Findings, verdict to validation, or Library definition to a model/theory automatically. |
| Board objects, versions, snapshots, links and Library groups | Visual surfaces and content history for scientific entities | Preserve visual history. Do not treat card types or labels as authoritative entity types, or board snapshots as immutable scientific versions. |
| `document_highlights`, text links, media slices, `vora_files` | Supporting source annotations and asset references | Preserve exact offsets, paths, hashes and timing. Offsets can become invalid if source content changes; paths may be machine-specific; no automatic semantic claim mapping. |
| Trace registry, graph JSON and decision Markdown | Operational history, project/decision context | Keep separate or import as clearly attributed Trace records. “Project,” “experiment,” “evidence” labels do not establish ResearchProject, ExperimentRun, or EvidenceArtifact. Preserve raw files and schema versions. |
| Market SQLite candles and Parquet tick assets | Inputs to an explicit dataset-ingestion workflow | Preserve both independently. No automatic DatasetVersion without a manifest for symbol/provider, time range, timezone, units, missingness, transformations, licensing and file hashes. |
| Worker queue tasks/logs/locks | Operational job history | Not ExperimentRun or AnalysisRun. Historical tasks may lack immutable inputs/outputs and can contain code/task payloads. Keep separate unless a reviewed adapter can prove provenance. |
| Portable imported-package tables and settings | Workspace import provenance/configuration | Keep separate from scientific package/entity provenance. The settings sidecar and SQLite DB need a defined joint restore policy. |
| Forge code entities and lineages | Code indexing lineage | Keep in Forge domain; canonical code entities are not scientific models or knowledge entities. |

### Unsafe transformations without additional evidence

Do not: delete/re-key legacy IDs; infer entity type from title/card `type` strings; convert time units by magnitude; derive exact observation units from free text; turn revision JSON into content versions; discard unknown JSON fields; merge duplicate-looking sources; create project ownership from directory names; assume external assets reside under one portable root; treat an empty/missing external file as user intent to delete a DB row; or overwrite original DBs during trial migrations.

## 3. Migration and backup controls

Before any production migration:

1. Establish a read-only inventory tool that records file hashes, app/schema evidence, table/column/index/FK metadata, row counts and external references without editing originals.
2. Obtain consented, anonymized fixtures for every supported schema generation and relevant edge state. Include populated and empty DBs, legacy schema files, mixed/partial initializer states if found, Market markers, sidecar settings, missing/existing external assets, and soft/dangling links.
3. Use copy-on-write/temp destination DBs. Take and verify SQLite online backups before upgrade; separately capture settings and every included external asset. Never mutate the only copy.
4. Introduce explicit ordered migration versions and one configured connection constructor. Run structural checks, `quick_check`, `foreign_key_check`, application-level reference validation, and asset-manifest checks before considering a migration successful.
5. Test atomicity with failures at each step, process termination/restart, repeated migration, rollback/recovery, concurrent connection use, and idempotent rerun. Emit explicit errors and conversion counts; never silently skip failed alterations.
6. Require a reviewed mapping report and approval for ambiguous records. Preserve raw source columns/files and legacy ID aliases until reconciliation is complete.
7. Test a full restore to a separate clean installation, including the DB, settings and declared external assets; compare canonical row/hash inventories and user-visible reopen behavior.

## 4. Concrete tests required by risk

| Risk group | Minimum tests |
|---|---|
| R1–R3 schema variance/ownership | Fresh schema parity; migration from each approved fixture; partial migration fixture; repeated migration; unknown column/table preservation; failure rollback; exact source-of-truth static check. |
| R4, R7, R10 integrity/relations | Assert FK pragma on each connection; inject dangling endpoints; `foreign_key_check`; endpoint type/cardinality validation; each delete/archive policy; relation traversal after restore. |
| R5 destructive migrations | Before/after row and hash counts; preserve source DB backup; markers unset/set; injected failure before/after deletion; safe repeat; explicit approval test for derived-only removal. |
| R6 backup/assets | Fixture with all referenced file classes; missing, moved and changed-hash assets; export/import into new directory; full reopen; rollback if asset staging fails; settings/DB consistency. |
| R8 provenance/revision atomicity | Source update plus revision commit/failure injection; immutable version hash; URL/document capture changes; old citation resolves after source update; append-only trigger behavior. |
| R9 timestamps/units | Seconds vs milliseconds; UTC boundaries and timezone/DST; exact fractional values/rounding; null/malformed/overflow; same instant round-trip across JSON, SQLite and DTOs. |
| R11 blobs/IDs | Historical JSON fixtures per observed shape; unknown fields retained; malformed shape quarantined with explicit error; duplicate ID/alias; source package round-trip. |
| R12–R14 identifiers/transactions/worker | Full cross-reference traversal; transaction failure at every write; duplicate/idempotent job execution; retry/cancel/stale lock; simultaneous worker/app use. |
| R15–R17 UI/docs/contracts | Restart and cache-clearing tests; browser vs Tauri mode; IPC serde round-trip; TypeScript/Rust DTO parity; tested UI persistence/error flows; audited docs link and schema claims. |

## 5. Residual unknowns

The following cannot be responsibly scored from repository source alone: actual deployed schema/version distribution; user data volume and relationships; prevalence of dangling references; whether external assets are backed up by user procedures; worker deployment and queue location; app behavior across supported platforms; all error suppression paths in previously shipped binaries; and domain meaning/units of user-authored free text or JSON. These require representative, user-approved data and product decisions, not speculative migration rules.
